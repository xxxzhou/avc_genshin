# 06 · AI 协作层 —— 意图到任务的全程自动化

> 本文档定 AI **全程处理**的落点:规划器(意图→任务组合)、代码生成/校验/缓存、失败反馈迭代、即时→持久提升、LLM 调用约定。
> 是 `00 §4`(AI 工作流)的展开;前置:`00`–`05`。
> **关键边界**:LLM 只在**规划/生成/修正**阶段介入(离线,允许 1–3s 延迟);**执行**阶段是纯 Python。这与运行时决策层(`01 §11`,后置)是两回事(§9)。

---

## 0. 一句话

AI 把"完成今天的日常"翻译成一组任务的执行计划;缺失的任务**现场生成**,失败的任务**据日志修正**——全程 LLM 介入,但**运行时零 LLM**(成本/延迟约束)。

---

## 1. AI 全程处理工作流(展开 `00 §4`)

```
① 意图理解   用户:"完成今天的日常并领奖"
   ↓
② 规划       Planner 读 registry.list() + 世界模型 → 分解为已有任务组合
             daily_quest(已存在) + claim_reward(已存在);缺失环节标记"需生成"
   ↓
③ 生成/复用  命中已有 → 直接复用;缺失 → LLM 生成符合 04 契约的脚本
   ↓
④ 校验       CodeValidator(AST 白名单 + 契约校验)→ 不通过则带错误回 ③
   ↓
⑤ 缓存       TaskCodeCache:intent → cache/tasks/<hash>.py(下次命中跳过 LLM)
   ↓
⑥ 执行       Runtime 纯 Python 执行(守护并发 + 取消 + 日志)【零 LLM】
   ↓
⑦ 反馈/迭代  失败 → 日志 failure(failure_type+截图)→ AI 据此定向修正 → 重新注册
   ↓
⑧ 提升       成熟的即时任务 → 移入 src/tasks/ → 持久任务(能力自我积累)
```

**②③④⑦⑧ = "AI 区"**(LLM 介入);**⑥ = "执行区"**(纯 Python)。

## 2. 规划器 Planner

```python
class Planner:
    def plan(self, intent: str, world: WorldModel) -> Plan:
        """意图 + 世界状态 → 执行计划"""
        candidates = registry.list()              # 枚举已注册任务(name/desc/params/tags)
        # LLM:把 intent 分解为已有任务的组合 + 标记缺失
        return Plan(steps=[...], missing=[...])
```

- **输入**:用户意图(自然语言)+ 世界模型状态(`g.has_flag`,今日做了什么)+ `registry.list()`(能复用什么)。
- **输出**:`Plan` = 已有任务序列(带参)+ 缺失任务清单(需生成)。
- **核心原则**:**优先组合已有任务**(复用),仅对缺失环节生成新代码——避免重复造轮子,能力随积累增长。

```python
@dataclass
class Plan:
    steps: list[PlanStep]        # [{task:"daily_quest", params:{count:4}}, ...]
    missing: list[MissingSpec]   # [{desc:"去采 5 朵甜甜花", reason:"无对应任务"}]
```

---

## 3. 代码生成

对 `Plan.missing` 的每一项,LLM 生成符合契约的脚本:

- **依据**:`04`(任务契约)+ `05`(可用 `g.*` API)+ `registry.list()`(避免与已有重复)。
- **产出**:一个 `@task` + `main(ctx,g,**params)` 的完整 `.py`(可直接落 `cache/tasks/`)。
- **prompt 组成**(§8 详述):系统角色 + 契约规范 + API 速查 + 已有任务清单 + 该缺失项的描述 + (迭代时)上次失败上下文。

> 生成阶段是 **AI 区**,允许 LLM 1–3s 延迟;生成结果**缓存**,后续相同意图毫秒级命中。

---

## 4. 校验 CodeValidator

生成的代码必须过两道校验,不过则带错误回 LLM 重生成(最多 N 次):

1. **AST 白名单**(安全):禁 `import`/`open`/`exec`/`eval`/`__import__`/下划线属性;仅允许白名单内置 + `framework`/`abilities` 的公开对象。
2. **契约校验**(规范):必须有 `@task` 或 `def main(ctx,g)`;`params` schema 合法;`name` 不与已注册冲突。

```python
class CodeValidator:
    def validate(self, code: str) -> tuple[bool, str]:
        ok, err = self._ast_whitelist(code)       # 安全
        if not ok: return False, err
        ok, err = self._contract(code)            # 规范
        return ok, err
```

> 校验失败的错误信息**回喂给 LLM**(如"第 5 行禁止 import,请用 framework 提供的 X"),让它定向修正,而非盲目重试。

## 5. 缓存 TaskCodeCache

```python
class TaskCodeCache:
    def get(self, intent: str) -> str | None:     # md5(intent) → cache/tasks/<hash>.py
    def put(self, intent: str, code: str): ...
    def invalidate(self, intent: str): ...        # 清缓存 → 重新生成
```

- **命中**:相同 intent 直接 `exec` 已缓存代码,**跳过 LLM**(1–3s → 毫秒级)。
- **失效**:改 intent / 手动清缓存 / 任务版本失效信号 → 重新生成。
- 缓存即"即时任务"(04 §7),成熟后提升为持久任务。

## 6. 反馈与迭代(失败回流)

执行失败时,日志(03 §7)记录结构化 `failure` 事件;AI 读它定向修正:

```
failure{failure_type=TemplateNotFound, path="daily/katherine.png", shot=...}
  → AI 判断:模板失效/ROI 偏移 → 更新模板或调整 g.find_template 区域
failure{failure_type=UnexpectedScene, expected=main_ui, got=unknown, shot=...}
  → AI 判断:出现未处理 UI → 在任务里补场景处理(如关弹窗)
failure{failure_type=StuckAt, pos=..., duration=30}
  → AI 判断:导航卡住 → 加脱出逻辑/换路径
```

- **failure_type → 修正动作**的映射见 `02 §4.3`;AI 据此**精准改局部**,而非整段重写。
- 修正后 `registry.reload(name)` 热加载 → 重跑 → 验证。形成闭环。

## 7. 提升机制(即时 → 持久)

```
即时任务(cache/tasks/<hash>.py)
   │  复用次数 ≥ N  或  成功率 ≥ X%  或  用户手动
   ▼
提升:移入 src/tasks/<name>.py + 补全 @task(name/desc/params/tags) + 提交 git
   ▼
持久任务(随包分发,规划器可复用)
```

- **触发条件**:复用次数/成功率阈值,或用户/AI 显式请求。
- **审定**:起步**待人工审定**(避免低质量任务污染 src);后续可配置自动提交。
- 这是框架能力**随使用自我积累**的机制(`00 §3.2`)——用得越多,可复用任务越多,LLM 生成越少。

## 8. LLM 调用约定(规划/生成阶段)

> 这是 **AI 区**的 LLM(规划/生成/修正),与运行时决策层(`01 §11`)不同(§9)。

**prompt 模板组成**:

```
[系统角色]   你是原神自动化任务的规划/生成器,输出必须符合契约。
[契约规范]   @task 字段 + main(ctx,g,**params)(04)+ 标准 API(05)
[可用 API]   g.* 速查 + 守护库 + 已注册任务清单(registry.list())
[世界模型]   当前状态(今日已做/树脂/位置)
[本次任务]   <意图/缺失项描述>
[迭代上下文] (仅修正时)上次失败 failure_type + 截图描述 + 出错代码段
[输出约束]   规划→JSON(任务序列);生成→单个 .py 文件内容
```

- **返回结构化**:规划返回 JSON(`Plan`);生成返回代码字符串(落 `.py`)。不用自由文本。
- **成本/频率**:规划/生成阶段调用,非每帧;缓存命中后零调用。
- **模型**:起步用 anthropic Claude(052 等);生成代码用强模型,规划可用较快模型。

## 9. 与运行时决策层(`01 §11`)的区分

| | **AI 协作层(本文,06)** | **运行时决策层(01 §11)** |
|---|---|---|
| 何时 | **离线**:规划/生成/修正阶段 | **运行时**:流程中遇不确定 |

| 现状 | 本框架的核心(现在做) | **预留接缝,后置**(M5 后) |

> 两者独立,勿混淆:06 是"AI 帮你写/改任务"(开发态),01 §11 是"任务跑到一半问 AI"(运行态)。本文只讲前者。

## 10. 可观测性回流

结构化日志(03 §7)不只是给人看,更是 **AI 的诊断数据源**:

- **单次失败**:读 `failure` 行 + 截图 → 定向修正(§6)。
- **趋势/失效**:某任务失败率上升 / `UNKNOWN` 场景增多 → **版本失效信号** → 提示 AI 重写(游戏更新致 UI 变化)。
- **回流面板**:聚合 `logs/` → 给 AI 一个"哪些任务不健康"的视图,驱动主动维护。

1. **规划器粒度**:LLM 一次性出完整 Plan,还是逐步(执行中按需规划)?起步一次性,复杂意图可分段。
2. **生成重试上限**:校验失败回 LLM 重生成,上限 N 次(N=3?)后转人工。
3. **提升自动化的安全**:自动提交到 src/tasks/ 的任务,如何保证不破坏已有(命名冲突/行为回归)——需测试(模拟执行,见下)。
4. **离线验证**:生成的任务能否在"录制回放"(模拟 avc)里先跑一遍再上线?需 mock 层(开放)。
5. **多模型分工**:规划/生成/修正用不同模型(成本/质量权衡)的策略。
