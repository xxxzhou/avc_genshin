> 本文档是 **avc_genshin** 在真实游戏里"跑得稳、AI 调得动、人敢放手"的地基设计。
> 前置:`01-执行引擎.md`(Runtime / 守护 / 同步桥 / 取消)。同层:`00-框架总纲.md`。
> 对照:BetterGI 的 `BgiVision`(场景状态机)+ 优先级/独占/`SupportedGameUiCategory` + 触发器互斥。

## 0. 为什么需要这一层

`01-执行引擎.md §8.2` 早先版本把守护与主任务的并发冲突说成"**极少、靠脚本 `mount` 顺序或 `suspend_all` 规避**"——这是**低估**。野外 `auto_pick` 在 `go_to` 期间按 F,会触发宝箱 / NPC / 七天神像 / 秘境入口 / 调查点的交互面板,立即破坏 `go_to` 的前提。这不是边缘情况,是野外高频副作用。BetterGI 正是用 `SupportedGameUiCategory` + 优先级/独占解决它的。

我们**放弃** BetterGI 那套"调度器侧"的复杂机制(优先级枚举、独占标志、UI 类别枚举——AI 难正确配置,也违背"代码即流程"),但**不放弃**它解决的正确性问题。本文用**更轻、更透明**的四个机制达到同等甚至更强的可靠性:

```
                       ┌──────────────────────────┐
        所有 g.* ─────▶│   SceneEstimator (§1)    │◀──── 守护场景门控 (§2)
        守护决策  ─────▶│  current_scene + 置信度   │      InputAuthority (§2)
                       └───────────┬──────────────┘
                                   │ 共享事实源 (SharedState)
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
   ┌─────────────────┐   ┌──────────────────┐   ┌─────────────────┐
   │ InputAuthority   │   │ Observe (§4)      │   │ Policy (§5)      │
   │ 输入通道权属·租约 │   │ 时间线·失败分类   │   │ 护栏·人类确认    │
   │ §2 并发可证明安全 │   │ §4 AI 迭代的眼睛  │   │ §5 AI 生成的信任 │
   └─────────────────┘   └────────┬─────────┘   └─────────────────┘
                                  │ 失败分类
                                  ▼
                          on_uncertain (01 §11) → 决策层(后置)
```

四个机制咬合:`SceneEstimator` 是**共享事实源**;`InputAuthority` 让并发模型**可证明安全**;`Observe` 让 AI 迭代**能收敛**;`Policy` 让 AI 生成**可被信任**。

> **与"代码即流程"的边界**:这四个机制都是**基础设施**,对任务作者大多**透明**(框架自动保证安全);作者只在需要时**显式声明**(`@daemon(owns_keys=..., scenes=...)`、`@task(needs_confirm=...)`)。它们**不规定流程怎么走**,只提供安全与可观测的运行环境——与 `00 §1.1` 的分层一致。

## 1. 场景估计器 SceneEstimator —— 共享事实源

### 1.1 问题

`01 §6` 的 `g.wait_main_ui` / `g.is_loading` 若写成"每次各自模板匹配",会出现:**每个 `g.*` 和每个守护都各自判一次场景**,逻辑分散、重复截图、结果可能不一致(主任务认为在主界面、守护认为在对话)。BetterGI 的 `BgiVision` 是一个**持续运行的状态机**,所有触发器和任务读同一个 `currentScene`——这是它可靠性的地基。

### 1.2 机制:一个常驻守护,持续输出 `current_scene`

```python
class Scene(Enum):
    MAIN_UI = "main_ui"          # 大世界主界面(可移动、可见小地图)
    COMBAT = "combat"            # 战斗中(血条/技能 UI)
    DIALOG = "dialog"            # 对话中
    MAP = "map"                  # 地图打开
    MENU = "menu"                # 背包/角色/设置/派蒙菜单等
    LOADING = "loading"          # 加载界面
    DOMAIN = "domain"            # 秘境内
    UNKNOWN = "unknown"          # 未识别(触发 on_uncertain)

@dataclass
class SceneState:
    scene: Scene
    confidence: float            # [0,1]
    since: float                 # 进入该场景的时刻(稳定判定用)
    sub: str | None              # 子类(如 MENU 下的 "inventory"/"settings")

class SceneEstimatorDaemon(Daemon):
    """常驻守护。以固定频率(如 5–10Hz)判一次场景,写入 SharedState。
    判定规则可组合:小地图有无 / 血条 UI / 对话框模板 / 加载特征 / OCR 关键词。"""
    name = "scene_estimator"
    async def run(self, ctx, token):
        while not token.cancelled:
            state = self._classify(ctx.capture())   # 复用 FrameDaemon 的帧(见 §3)
            Runtime.instance().shared.scene = state
            await asyncio.sleep(0.1)
```

### 1.3 所有读取方都问 `SharedState.scene`,不再各自匹配

- `g.wait_main_ui(timeout)`:等 `scene==MAIN_UI` 且 `since` 稳定 N 帧,而非自己轮询模板。
- 守护的场景门控(§2)读它。
- `Observe`(§4)时间线读它,记录每步的 scene。

### 1.4 与 BetterGI 对照

| BetterGI `BgiVision` | avc_genshin `SceneEstimator` |
|---|---|
| 状态机类 + 每帧由调度器驱动 | 自治 async 守护,自己循环 |
| 场景枚举写在 C# 代码里 | `Scene` 枚举 + 规则可配置;UNKNOWN 回流给 AI 迭代(§4) |
| 全局单例 `currentScene` | `SharedState.scene`(RunContext 内,单次运行隔离) |

### 1.5 开放问题

- **分类法随版本演进**:游戏更新致 UI 变化时,`UNKNOWN` 比例上升——由 `Observe`(§4)捕获并回流给 AI,补充判定规则(可热加载,与任务热加载同机制)。

## 2. 并发权属 InputAuthority + 场景门控 —— 并发可证明安全

### 2.1 问题(修正 `01 §8.2`)

单线程 loop 解决了 avc 的**线程安全**(同线程调用),但没解决**逻辑并发**:多个协程在 await 点交错,都可能发输入。`auto_pick`(按 F)与 `go_to`(压 WASD + 移动鼠标)并存时,F 的副作用会打断导航。必须由**框架**保证不互踩,而非靠任务自觉。

### 2.2 机制一:输入通道权属(InputLease)

把输入按**通道分组**,守护/主任务**声明并租用**它要用的通道;`InputAuthority` 保证同一通道同一时刻只有一个写者(或按优先级仲裁):

```python
class InputChannel(Enum):
    MOVE = "move"              # W/A/S/D(移动)
    INTERACT = "interact"      # F(交互/拾取)
    COMBAT = "combat"          # E/Q/普攻/num1~4(战斗)
    MENU = "menu"              # Esc/M/Tab/J(开菜单)
    MOUSE_MOVE = "mouse_move"
    MOUSE_CLICK = "mouse_click"

class InputAuthority:
    def acquire(self, channels: set[InputChannel], holder: str,
                priority: int = 0) -> InputLease: ...
        # 空闲 → 直接授予;被低优先级持有 → 抢占(低优先级在该通道 suspend);
        # 被同/高优先级持有 → 抛 InputConflict(默认)或返回空租约(可选)。
    def release(self, lease: InputLease): ...
```

- **守护**:`@daemon(owns_keys={InputChannel.INTERACT})` 在 mount 时 acquire,unmount/suspend 时 release。
- **主任务的 `g.*`**:高层 API 内部隐式租用。`g.go_to(pos)` 执行期间持有 `{MOVE, MOUSE_MOVE}`,结束释放;`g.click()` 持有 `{MOUSE_CLICK}` 瞬时释放。
- **这就让"边走边拾取"合法且安全**:`go_to` 持 `{MOVE}`,`auto_pick` 持 `{INTERACT}`,**通道不重叠 → 共存**;而两个都想持 `{INTERACT}` 的守护 → 冲突被框架拒绝。

### 2.3 机制二:场景门控(scenes=)

守护声明它**只在哪些场景活跃**;由 `SceneEstimator`(§1)判定,不符自动 suspend,无需守护作者手写 `if scene == ...`:

```python
@daemon(
    name="auto_pick",
    owns_keys={InputChannel.INTERACT},
    scenes=[Scene.MAIN_UI, Scene.DOMAIN],   # 对话/菜单/战斗里根本不启动
    priority=0,
)
class AutoPickDaemon(Daemon): ...
```

- 框架在守护每次循环迭代前检查 `shared.scene.scene ∈ scenes`,不符则 `await` 挂起到场景恢复。
- 效果:`auto_pick` 在对话/地图/菜单/战斗中**自动静默**——从根上消掉"误按 F 弹面板""战斗中误拾取"。

### 2.4 冲突仲裁规则

| 情况 | 框架行为 |
|---|---|
| 两守护声明通道不重叠 | 共存(边走边拾取) |
| 两守护声明同通道、不同 priority | 高优先级抢占,低优先级在该通道 suspend |
| 两守护声明同通道、同 priority | **后 mount 者被拒**(抛 `InputConflict`,带双方名)——AI 据此修正 |
| 守护通道 ⊂ 主任务当前租用 | 拒绝守护(主任务优先),或由 `priority` 决定 |
| 主任务进入"不可打断段" | 显式 `ctx.suspend_all()`(如战斗连招/设置菜单)——逃生口,非并发安全依赖 |

### 2.5 与 BetterGI 对照

| BetterGI | avc_genshin |
|---|---|
| `Priority` / `IsExclusive` / `SupportedGameUiCategory` 由调度器侧仲裁 | **输入通道租约** + **场景门控**,声明式、可证明 |
| 触发器无自身控制流,由调度器筛选同帧运行 | 守护自有循环,框架只在 acquire/场景检查处把关 |
| 冲突靠调度器优先级枚举(复杂、AI 难配) | 冲突靠通道不相交(简单、AI 易写对) |

> **修订 `01 §8.2`**:并发安全**不是**"极少、靠 AI 自觉",而是由 `InputAuthority` + 场景门控**框架保证**。`suspend_all` 降级为"不可打断段"的显式逃生口。

## 3. 推理调度(共享帧) —— 不让 YOLO@10Hz 饿死主任务

### 3.1 问题

`01 §4.2` 的 `AutoPickDaemon` 自己 ~10Hz 截图 + YOLO 推理。若多个守护(auto_pick / has_enemy / find_nearest_enemy)各自截图+推理,单线程 loop 会被吃满,主任务的 `go_to` 循环被严重拖慢(`01 §10.1` 已提此风险)。

### 3.2 机制:单一 FrameDaemon 截图+推理,广播结果

```python
class FrameDaemon(Daemon):
    """唯一截图 + 推理者。按固定频率(自适应:移动时 10Hz,静止时 2Hz)跑一次,
    把 {frame, detections, scene_hint} 广播给所有订阅者。"""
    name = "frame"
    async def run(self, ctx, token):
        while not token.cancelled:
            frame = ctx.capture()
            dets = await self._infer_async(frame)     # onnxruntime 推理(释放 GIL)
            self._publish(frame, dets)                # 订阅者(auto_pick/SceneEstimator/...)各取所需
            await asyncio.sleep(self._adaptive_dt())
```

- **共享帧**:一次截图 + 一次推理服务所有消费者,避免重复。
- **自适应频率**:由 `SceneEstimator`/主任务状态决定(移动中高频、静止/菜单低频)。
- **性能纪律**:重活(截图、YOLO/OCR 推理)下沉 avc(C++)或 onnxruntime(释放 GIL);Python 只做编排与决策。**绝不**在 Python 写逐像素热循环——这是相对 BGI(全 C#)的固有劣势的纪律性补偿。

### 3.3 与 BetterGI 对照

BGI 调度器天然"每帧截图一次、分发所有触发器",等于内置了共享帧。我们用 `FrameDaemon` 守护达到同样效果,且频率自适应、消费者显式订阅。

## 4. 可观测性 Observe —— AI 迭代能收敛的 substrate

### 4.1 核心论点

这个框架的闭环是 **AI 生成 → 跑 → 观察 → AI 修正**。观察环节的质量**直接决定任务能否收敛**。BGI 是开发者在屏幕前 debug;**AI 没法坐到屏幕前**——系统必须抓全诊断信息让 AI 远程定位。这不是"日志",是**AI 的眼睛**。这是"AI 生成代码"模式独有的刚需,BGI 不需要。

### 4.2 机制一:执行时间线 Timeline

每次运行记录一条**结构化时间线**,而非松散日志:

```
t=12.30  scene=MAIN_UI   action=press(W,hold=200)            result=ok
t=12.40  scene=MAIN_UI   detect={interact:[(x,y,0.91)]}
t=12.50  scene=DIALOG(!) action=press(F)                     result=opened_chest
t=12.55  expected=MAIN_UI got=DIALOG  ← 异常点,自动存证
```

```python
class Observe:
    def event(self, kind: str, **fields): ...      # 追加一条(自动带 t/scene)
    def timeline(self) -> list[TimelineEntry]: ... # 供 AI 回流诊断
```

`scene` 字段来自 `SceneEstimator`(§1)——时间线天然带场景上下文。

### 4.3 机制二:结构化失败分类

不是笼统的 `TaskError`,而是**定向的失败类型**,AI 拿到能精准修:

| 失败类型 | 触发 | AI 据此能做什么 |
|---|---|---|
| `UnexpectedScene(expected, got)` | 场景估计器报不一致 | 补场景处理/调整等待 |
| `TemplateNotFound(path, region)` | `g.wait_template` 超时 | 更新模板图/调整 ROI/阈值 |
| `StuckAt(pos, scene, duration)` | 看门狗:位置/场景异常持续 N 秒 | 加脱出逻辑/换路径 |
| `InputConflict(channels, holders)` | `InputAuthority` 拒绝(§2) | 改守护通道声明/mount 顺序 |
| `Timeout(stage, waited)` | 某 stage 超时 | 拆分 stage/加重试 |
| `PolicyViolation(rule)` | 护栏拦截(§5) | 改任务行为(不该花钱) |

### 4.4 机制三:失败自动存证

`g.wait_template` 超时 / 场景异常 / 看门狗触发时,**自动存**当时截图 + 期望 + 实际 scene + 最近 N 步时间线到 `debug/<run_id>/`,而非只打一行 timeout。AI 读这些就能定位,不必整段重写。

### 4.5 机制四:种子可复现

拟人化 RNG(`ic.setJitterSeed`)可固定种子,使一次失败的运行能**复现**——对着复现的轨迹改脚本,而非靠运气。

### 4.6 与决策层衔接

失败分类 → `Runtime.on_uncertain(event)`(01 §11)→ 决策层(后置)。`UNKNOWN` 场景、`StuckAt` 等是被动求救的天然触发源。**现在只接 `Observe` 存证,决策层接入后自动复用同一事件流。**

### 4.7 绑定:能力可观测(每个 ability 发「看/选/结果」事件)

**这是本节 §4 的落地产物,也是绑定规则**——光有时间线不够,必须让**每个 ability** 在决策点主动发结构化事件,AI 才能从输出**点名坏在哪个 ability 的哪个 stage/reason**。完整 schema(字段表 + 节流模式 + reason slug 目录)见 `设计实现.md §2`,本节只给 kind 目录与读端。

**写端(observe.py)**:`event(kind, ability=..., phase=..., ok=..., reason=..., **facts)`。`ctx.observe`/`g.observe` 永可调用(无 runtime 时返 `_NullObserve` no-op 单例,代码**不得判空**)。

**kind 目录**(domain 固定集 `<domain>.<stage>`):

| domain | 代表 kind | ability | 诊断什么 |
|---|---|---|---|
| `tp` | `tp.resolve`/`tp.navigate`/`tp.confirm`/`tp.icon` | tp | 传送点选错/确认卡住 |
| `nav` | `nav.step`/`nav.stuck` | nav / trap | 走偏、卡地形、脱出失败 |
| `pos` | `pos.match`/`pos.bigmap` | pos | 定位层选错/无覆盖 |
| `cam` | `cam.rotate`/`cam.heading_fail` | cam | 朝向读不到、转不到 |
| `path` | `path.segment`/`path.action` | path | 路径段失败、动作未处理 |
| `fight` | `fight.enemy`/`fight.burst` | fighter | 找不到怪、没放大 |
| `survive` | `survival.check`/`survival.revive`/`survival.low_hp` | fighter | 死了没复活、血少没吃药 |
| `detect` | `detect.template`/`detect.ocr`/`detect.ui`/`detect.blood`/`detect.classify` | vision_utils / game_state / fighter | 模板/OCR/UI/血条/分类 |
| `reward` | `reward.claim` | reward | 树脂没找到、领奖失败 |
| `panel` | `panel.detect` | tp_panel | 面板类型/关键词 |
| `task` | `<task>.step`(如 `daily.step`/`auto_ley_line.step`) | 任务名 | 子任务级成败 |

**热轮询防爆**:scene 分类器 10Hz、`wait_*` 5Hz、auto_eat 6.6Hz 传 `_quiet=True`(同 key 整 run 只发首条)或 `throttle_key=`(1s 窗口折叠,`ok=False` 永不被节流)。**节流优先级**:`_quiet`/`_transition` 显式模式 > 「ok=False 永不节流」 > 时间窗口。

**读端(report.py,与 observe.py 写端分离)**:`live_line(event)`→一行 `<ability> <kind> <ok|reason|keyfact>`(runtime 注册订阅者实时打 stderr);`summarize(timeline)`→按 `ability` 分组 `{ok_count, fail_count, failures:[{stage,reason,...}]}`;`runtime._teardown` 在 `run_end` 前发 `run_summary`(带 `summarize` 结果)。**AI 定位规则**:筛 `ok==False` 或检测 0/异常 → 该事件 `ability` 即嫌疑 → 看 `reason` slug 定分支。`python main.py --task verify probe=timeline` 可实时看事件流。

## 5. 护栏层 Policy —— 让 AI 生成可被信任

### 5.1 核心论点

BGI 的任务是**人写的**,人不会写"把原石全抽了"。但 AI 会——它可能为"清理背包"误花货币、误进联机、误删东西。这是"AI 生成代码"模式**独有**的风险,BGI 不需要它。要让"AI 全程处理"**可被信任**,必须有框架强制的护栏。

### 5.2 机制:声明式 Policy,沙箱强制执行

```python
@dataclass
class Policy:
    never_spend: list[str] = field(default_factory=list)   # ["primogem","stardust"]
    no_coop: bool = False                                  # 不进联机
    regions: list[str] | None = None                       # 只在这些区域活动
    time_budget_s: int | None = None                       # 单次运行上限
    confirm_threshold: str = "medium"                      # high|medium|low:高风险动作执行前人类确认
```

- **沙箱拦截**:AI 任务的每次 `g.*` 调用经 `Policy` 校验。会消耗 `never_spend` 的操作 → 抛 `PolicyViolation`(进 §4 失败分类);超 `time_budget` → 取消;越 `regions` → 拒绝移动。
- **人类确认**:高风险动作(花钱、删除、进入特定流程)按 `confirm_threshold` 暂停并通知人类,获确认后继续。
- **任务自声明**:`@task(needs_confirm=True)` 让单任务强制走确认,即使全局阈值宽松。

### 5.3 与 BetterGI 对照

BetterGI 无此层(人写代码、人负责)。avc_genshin 因 AI 生成代码而**必须有**——这是让人类敢放手让 AI 跑的前提,也是 §0"人敢放手"的落点。

## 6. 四件套如何咬合(端到端示例)

意图:**野外走至 NPC 并对话,途中自动拾取**。

```
任务: g.go_to(npc_pos) 期间 ctx.mount("auto_pick"); 到达后 g.talk("领取奖励")

① SceneEstimator 持续输出 scene=MAIN_UI
② g.go_to 持有 {MOVE, MOUSE_MOVE};auto_pick 申请 {INTERACT} + scenes=[MAIN_UI]
   → 通道不重叠,InputAuthority 准许共存 → 边走边拾取(合法)
③ 路过宝箱,auto_pick 按 F → 开箱 → SceneEstimator 报 scene=DIALOG(宝箱面板)
   → auto_pick 的 scenes 门控立刻 suspend(不在 MAIN_UI)→ 不会狂按 F
   → 主任务 go_to 的 wait_main_ui 失效?不:g.go_to 内部等待 scene 回 MAIN_UI(§1.3)
④ 假设卡死 30s(位置不变)→ 看门狗报 StuckAt → Observe 存证(截图+时间线)
   → on_uncertain 触发(决策层后置;现在走原失败处理/通知人类)
⑤ 全程若 AI 误生成"花原石传送":Policy 拦截 → PolicyViolation → AI 据此修正
```

每一步的可靠性都由框架保证,任务作者只写 `g.go_to` / `ctx.mount` / `g.talk`——**流程是纯 Python,安全是基础设施**。

## 9. 开放问题

1. **Scene 分类规则的工程化**:用模板/OCR/小地图特征的组合规则,还是训一个小分类器?起步用规则(可热加载),UNKNOWN 比例高时再升级。
2. **InputChannel 粒度**:分组(MOVE/INTERACT/...)vs 单键?起步用分组(够用且 AI 易声明);若不够再细化。
3. **看门狗阈值**:StuckAt 的"位置不变 N 秒"在不同任务(站桩战斗 vs 走路)下应不同——由任务声明 `expected_progress` 或用 scene 区分。
4. **Policy 的 `never_spend` 如何识别**:消费类操作怎么映射到货币?需要 `g.*` 的"语义化操作"标注(如 `g.spend(currency, amount)`)。
5. **人类确认通道**:无 UI 框架下,确认走 CLI 提示 / 桌面通知 / 手机推送——与运行时决策层的 `ask_human`(01 §11)共用通道。
