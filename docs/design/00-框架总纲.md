# 00 · 框架总纲 —— 以 AI 动态添加任务为核心的插件式框架

> 本文档是 **avc_genshin** 的架构纲领。它定义"框架是什么、AI 在其中扮演什么角色、任务如何被动态添加与运行"。
> 下层文档:`01-执行引擎.md`（Runtime / 守护任务 / 取消）。
> 参照:`设计实现.md`、`genshin_daily_design.md`、BetterGI 框架分析(`docs/bgi-framework/`)。

---

## 1. 一句话定位

**一个让 AI 能持续、动态地添加游戏自动化任务的 Python 框架。**
底层通用能力（视觉/输入）由 **avc（C++ SDK）** 提供；
原神领域的框架能力（任务体系、运行时、高层 API、守护库、导航/战斗）由 **avc_genshin** 提供；
具体的业务任务（领日常、刷秘境、采集…）**由 AI 生成并作为插件动态加入**框架。

> **最高原则：框架必须为"AI 来添加任务"而设计。** 一切机制——任务契约、注册发现、生命周期、API 表面——都要让 AI 写得来、加得进、跑得起、调得动。

### 1.1 设计哲学：Python 代码即流程（澄清"无框架/无状态机/无轮询"）

`genshin_daily_design.md` 所说的"**无框架、无状态机、无轮询调度**"，针对的是 BetterGI 那种模式——**用 JSON 描述固定流程 + C# 状态机类驱动 + 中央定时器轮询回调触发器**。本项目用 Python，**流程直接用 Python 代码表达**（`if/else`、`while`、`for`、`await`、函数调用），比设计 JSON 固定流程更灵活、AI 也更擅长生成。

必须严格区分两层，避免把"基础设施"误读成"流程框架"：

| 层 | 是什么 | 是否"框架" |
|---|---|---|
| **流程层**（任务的业务逻辑） | 纯 Python 代码：`if`/`while`/`for`/`await`/`mount`/`ctx.run` | **无 JSON、无状态机类、无中央轮询调度器。代码即流程。** |
| **基础设施层**（给流程提供运行环境与能力） | Runtime（运行/取消）、任务注册表（发现/热加载）、沙箱（安全）、守护库、高层 API | 是"底座"，提供能力，**但不侵入流程控制**——流程怎么走完全由 Python 代码决定。 |

> 一句话：**Runtime 负责"安全地跑你写的 Python"，不负责"规定你怎么写流程"。**

与 BetterGI 抛弃项的精确对照：

| BetterGI（要抛弃的） | 本项目（Python 代码即流程） |
|---|---|
| JSON 描述战斗/路径流程，引擎解析后执行 | 流程就是 Python 函数体，直接运行 |
| `StateMachineBase<TState,TContext>` 状态机类驱动 UI 自动化 | 用 `while`/`if` + `g.wait_*` 直接写 |
| `TaskTriggerDispatcher` 中央定时器**每帧回调**所有 `ITaskTrigger`（触发器无自身控制流） | 守护任务是**自己的 `while+sleep` 循环**，控制流在守护自己手里，**无中央调度器** |

> 注意：守护任务的"自己循环"在字面上也是轮询，但本质区别在于**控制流归属**——BetterGI 是"调度器调你"，本项目是"你自己循环、框架只提供取消信号"。前者是框架驱动流程，后者是代码即流程。

## 2. 三层架构

```
┌────────────────────────────────────────────────────────────────┐
│  L3  AI 任务插件  (tasks/*.py)            ← AI 动态生成并添加    │
│      daily_quest / farm_domain / collect_flowers / fish_all …   │
│      遵循任务契约，可被注册、发现、组合、调用                       │
├────────────────────────────────────────────────────────────────┤
│  L2  avc_genshin 框架  (本仓库, Python)   ← 游戏领域框架         │
│   ┌─ 任务体系 ──────────────────────────────────────────────┐   │
│   │  任务契约  •  注册表/发现/热加载  •  任务组合(编排)        │   │
│   ├─ 执行引擎 (Runtime) ─────────────── 见 01-执行引擎.md ───┤   │
│   │  沙箱  •  守护任务库  •  取消/超时  •  并发(协程)          │   │
│   ├─ 原神领域能力 ───────────────────────────────────────────┤   │
│   │  高层游戏 API (g.*)  •  导航(PathExecutor)  •  战斗        │   │
│   │  游戏状态检测  •  小地图定位  •  守护(auto_pick/skip/…)   │   │
│   ├─ AI 协作层 ───────────────────────────────────────────────┤   │
│   │  AI 规划器(意图→任务)  •  代码生成/校验/缓存  •  可观测性   │   │
│   └────────────────────────────────────────────────────────────┘ │
├────────────────────────────────────────────────────────────────┤
│  L1  avc  (C++ SDK, SWIG→Python)          ← 通用 CV+IO 能力    │
│   IScreenCapture(截图)  •  IInputController(输入+拟人化)         │
│   ITemplateMatcher  •  ITextRecognizer(OCR)  •  ONNX 推理        │
└────────────────────────────────────────────────────────────────┘
```

### 谁提供什么（边界清晰，避免 AI 重复造轮子）

| 能力 | 提供层 | 说明 |
|---|---|---|
| 截图 / 键鼠输入 / 拟人化 | **L1 avc** | `Input`、`IScreenCapture`、`IInputController` |
| 模板匹配 / OCR | **L1 avc** | `ITemplateMatcher`、`ITextRecognizer` |
| ONNX 推理（YOLO 等） | **L1 avc** 或 onnxruntime Python | 见 设计实现.md §3.2.2 |
| YOLO 输出解码 / 模型加载 | **L2 框架** | `GenshinDetector`（BetterGI YoloSharp 格式） |
| 高层游戏 API（`g.teleport_to/go_to/talk`） | **L2 框架** | 封装 avc，面向 AI |
| 守护任务（auto_pick/skip/loading…） | **L2 框架** | 可复用的并发响应器 |
| 导航 / 战斗 / 状态检测 | **L2 框架** | `PathExecutor`、`SimpleFighter`、状态判断 |
| 任务契约 / 注册表 / Runtime / 沙箱 | **L2 框架** | 本框架基础设施 |
| 具体业务流程（领日常、刷本…） | **L3 AI 插件** | AI 生成，调用 L2 能力 |

## 3. 核心概念：Task（任务）是一等公民

框架的一切围绕"任务"组织。**任务是可被 AI 添加、注册、发现、组合、运行的单元。**

### 3.1 任务契约（Task Contract）

AI 添加任务时遵循的统一格式。轻量、自描述、易生成：

```python
# tasks/daily_quest.py —— 一个任务插件
from framework import task

@task(
    name="daily_quest",                 # 唯一名（注册键）
    desc="完成每日委托并领取奖励",        # AI 规划时据此判断是否复用
    daemons=["auto_skip"],              # 运行时自动挂载的守护（见 01-执行引擎.md）
    requires=["navigation"],            # 声明依赖的领域能力（供规划器校验）
    params={                            # 参数 schema（AI 据此传参）
        "count": {"type": "int", "default": 4, "desc": "委托数量"},
    },
)
def main(ctx, g, count=4):
    """ctx=GameContext, g=高层API。返回 dict 或抛异常。"""
    g.teleport_to("蒙德城")
    ctx.mount("auto_pick")
    g.go_to(katherine_pos)
    ctx.unmount("auto_pick")
    g.talk("领取每日委托奖励")
    return {"claimed": True}
```

**契约要素**：
1. **元数据**：`name`/`desc`/`daemons`/`requires`/`params` —— 让框架和 AI 都能"读懂"这个任务。
2. **入口**：`main(ctx, g, **params)` —— 统一签名，AI 无需猜测。
3. **返回 / 异常**：标准 dict 返回 + 框架定义的异常类型（`NormalEnd`/`Retry`/`TaskError`）。

> 设计要点：装饰器形式对 AI 极友好——模式固定、字段自解释，LLM 一次生成即可命中规范。框架也接受"无装饰器的极简脚本"（仅 `def main(ctx,g):`）作为降级形态。

### 3.2 任务的两种形态

| 形态 | 来源 | 生命周期 | 典型 |
|---|---|---|---|
| **持久任务** | AI 写入 `tasks/*.py` | 注册进注册表，按名调用、可组合、跨会话复用 | `daily_quest`、`farm_domain` |
| **即时任务** | 用户 intent → AI 现场生成 | 缓存到 `cache/tasks/<hash>.py`，执行完即弃（可选提升为持久任务） | "去采 5 朵甜甜花" |

**提升路径**：即时任务若效果好，AI/用户可将其"提升"——从 cache 移入 tasks/ 并补全元数据，成为持久任务。这让框架的能力随使用**自我积累**。

### 3.3 任务可组合（Python 代码组织，非配置编排）

一个任务的 `main` 里可以直接调用其他任务——纯 Python 函数调用，**不是** BetterGI 那种 JSON 配置组 / 一条龙：

```python
@task(name="one_dragon", desc="一键日常")
def main(ctx, g):
    ctx.run("claim_mail")               # 调用持久任务
    ctx.run("craft_resin")
    ctx.run("daily_quest", count=4)
    ctx.run("farm_domain", name="绝缘", times=3)
    return {"all_done": True}
```

`ctx.run(name, **params)` 由 Runtime 保证串行与上下文隔离。AI 规划复杂意图时，优先**组合已有任务**，仅对缺失环节生成新代码。

## 4. AI 全程处理工作流

"全程"指**任务的开发生命周期全程由 AI 处理**，而非运行时每帧调 LLM（成本/延迟约束，见 design.md §12.7）。

```
┌──────────────────────────────────────────────────────────────┐
│  ① 意图理解    用户:"完成今天的日常并领奖"                      │
│      ↓                                                        │
│  ② 规划        AI 读"任务注册表"→ 分解为已有任务的组合           │
│                daily_quest(已存在) + claim_reward(已存在)       │
│                缺失环节 → 标记为"需生成"                        │
│      ↓                                                        │
│  ③ 生成/复用   命中已有任务 → 直接复用                          │
│                缺失 → AI 生成符合契约的脚本 → 校验 → 注册        │
│      ↓                                                        │
│  ④ 编排        生成一个"编排任务"调用上述任务序列                 │
│      ↓                                                        │
│  ⑤ 执行        Runtime 串行执行编排任务（纯 Python，无 LLM）     │
│                守护任务并发；取消/超时保护；日志/截图可观测        │
│      ↓                                                        │
│  ⑥ 反馈/迭代   失败截图 + 日志回流给 AI → 修正任务脚本 → 重新注册 │
│                成熟的即时任务 → 提升为持久任务                    │
└──────────────────────────────────────────────────────────────┘
```

**关键**：步骤 ②③④是"AI 区"（LLM 介入），步骤 ⑤是"执行区"（纯 Python）。LLM 只在规划/生成/修正时介入，不在实时操作中调用。

## 5. 动态添加与发现机制（框架的核心）

这是"框架符合 AI 来添加"的落点：

### 5.1 任务注册表（Task Registry）

```python
class TaskRegistry:
    """name → TaskDescriptor。框架启动时扫描 tasks/，运行时可动态注册。"""
    def register(self, task_or_path): ...     # 注册一个任务（文件或对象）
    def get(self, name) -> TaskDescriptor      # 按名取
    def list(self, filter=None) -> [...]       # 供 AI 规划器枚举（名+desc+params）
    def reload(self, name): ...                # 热重载单个任务（AI 修改后）
```

### 5.2 发现与热加载

- **启动扫描**：框架启动时扫描 `tasks/**/*.py`，凡含 `@task`（或 `def main(ctx,g)`）的模块自动注册。
- **热加载**：AI 修改/新增任务文件后，`registry.reload(name)` 立即生效，**无需重启**。文件变更可由 watcher 自动触发。
- **动态注册**：AI 也可不经文件，直接 `registry.register(TaskObject)` 注册内存任务（即时任务走这条）。

### 5.3 AI 添加一个任务的完整路径

```
AI 生成符合契约的 tasks/collect_flowers.py
   → 写入文件
   → TaskRegistry 自动发现并注册（或显式 register）
   → 立即可被 ctx.run("collect_flowers", count=5) 调用
   → 立即可被 AI 规划器在分解意图时复用
```

> 这条路径的顺畅度是框架成败的核心指标：AI 写一个文件，框架即接纳、即暴露、即可组合。

## 6. 框架如何"符合 AI 来添加"（设计原则清单）

| 原则 | 含义 | 落点 |
|---|---|---|
| **契约简单自描述** | AI 看一眼就知怎么写 | `@task` 装饰器 + `main(ctx,g)` |
| **添加无需重启** | 写文件即生效 | 热加载 / 文件 watcher |
| **标准 IO** | 参数/返回/错误统一 | `params` schema + dict 返回 + 标准异常 |
| **可组合** | 任务调任务 | `ctx.run(name)` |
| **可复用** | 写一次永久可用 | 持久任务 + 注册表 |
| **高层 API** | AI 写得少错得少 | `g.teleport_to/go_to/talk`（见 01 §6） |
| **可观测** | AI 能调试迭代 | 结构化日志 + 失败截图 + 回放（`debug/`） |
| **安全沙箱** | AI 代码不破坏宿主 | AST 白名单 + 超时 + 取消（见 01 §5） |
| **能力清单可发现** | AI 知道能用什么 | avc API 文档 + 守护库 + 已注册任务清单 |

## 7. 与 BetterGI 的理念对照

| 维度 | BetterGI | avc_genshin |
|---|---|---|
| 任务来源 | 开发者用 C#/JS 硬编码 + JSON 编排 | **AI 动态生成并添加** |
| 框架角色 | 固定的调度器，任务被动接入 | **接纳 AI 任务的容器**，任务是一等公民 |
| 扩展方式 | 改 C# 代码重编译 / 写 JS 脚本 | **写一个 .py 文件即插件** |
| 编排 | 硬编码一条龙 + JSON 配置组 | AI 现场组合已有任务 |
| 能力积累 | 版本发布 | **随使用自我积累**（即时→持久） |
| 谁主导 | 开发者 | **AI 全程，人类给意图** |

> 借鉴 BetterGI 的：双回路思想（主任务 vs 守护）、上下文分层、取消模型、1080p 归一化、ONNX 模型/路径数据复用。
> 摒弃的：定时轮询调度器、优先级/独占/UI 场景枚举、JSON 战斗编排、硬编码状态机。

## 10. 开放问题

1. **任务依赖与能力声明校验**：`requires=["navigation"]` 是仅文档，还是框架强制校验能力已加载？
2. **任务版本与兼容**：任务脚本随游戏更新失效时，如何让 AI 感知并重写（可观测性回流）。
3. **并发任务的资源隔离**：多个编排任务排队时，GameContext 单例如何隔离（串行 vs 快照）。
4. **守护任务参数化**：`ctx.mount("auto_pick", whitelist=[...])` 的参数注入约定。
5. **失败回流的格式**：截图+日志如何结构化，便于 AI 精准定位并修正（而非整段重写）。
