# 01 · 执行引擎设计（对照 BetterGI）

> 本文档是 **avc_genshin**（C++ 底层 avc + Python 业务层）的执行引擎设计。
> 参照 `设计实现.md`（avc Python API / GameContext / ScriptRunner）与 `genshin_daily_design.md`。
> 对照 BetterGI 执行引擎（`docs/bgi-framework/00-主体框架.md` §4）。
>
> **一句话定位**：新项目的"执行引擎"不是 BetterGI 那种**游戏调度器**（定时轮询 + 触发器），
> 而是一个 **AI 脚本运行时（Runtime）**——加载、校验、沙箱执行 AI 生成的 Python 脚本，
> 并提供脚本运行所需的**并发（守护任务）、取消、生命周期**管理。

---

## 1. 为什么重新定义"执行引擎"

| | BetterGI | avc_genshin |
|---|---|---|
| 脚本语言 | ClearScript V8（JS） | Python（AI 生成） |
| 执行引擎职责 | **调度游戏**：定时器每帧截图 → 分发触发器 → 跑任务 | **运行脚本**：加载/校验/沙箱执行 AI 脚本 + 并发守护 |
| 调度方式 | `TaskTriggerDispatcher` 轮询 + `ITaskTrigger` 回调 | **无轮询**：脚本自有控制流，守护任务用协程并发 |
| 编排方式 | JSON 战斗脚本 + 硬编码状态机 | AI 生成 Python，无 JSON、无状态机 |

`genshin_daily_design.md` 的核心原则是「**无框架、无状态机、无轮询调度**」。但 BetterGI 用**实时触发器**解决的一个需求客观存在：**移动过程中并发响应**（走动中自动按 F 拾取、自动跳对话、加载自动等待）。

`设计实现.md` 的 `AutoPick.tick()` 写了"每帧调用"，却没定义**谁调用它**——这正是执行引擎要补的空白。我们用一个**比触发器更轻量的机制**解决：**协程守护任务（Daemon）**。

### 设计目标

1. **AI 能快速编写脚本** —— 暴露高层语义 API，AI 写得少、错得少；同步代码，不要求 AI 学 `async/await`。
2. **快速加载脚本** —— intent → 缓存 → 热加载，命中缓存毫秒级启动。
3. **AI 脚本运行能力** —— 沙箱 + 超时 + 统一取消 + 并发守护。

## 2. 与 BetterGI 执行引擎的映射

不是照搬，是**思想借鉴、形态重塑**：

| BetterGI（`GameTask/`） | avc_genshin | 借鉴点 / 变化 |
|---|---|---|
| `ISoloTask` + `TaskRunner`（独立任务，信号量互斥） | **主脚本**（AI 生成的同步流程）+ `Runtime` 执行 | 保留"单一主任务"串行语义；去掉 `TaskSemaphore`，Runtime 天然串行 |
| `ITaskTrigger` + `TaskTriggerDispatcher`（每帧回调） | **守护任务 Daemon**（async 协程，`mount/unmount`） | 从"被调度器回调"变成"自己的 async 循环"；去掉优先级/独占/UI 场景枚举 |
| `TaskContext`（游戏会话级） | `GameContext`（avc 实例，见 设计实现.md §3.2.1） | 直接复用 |
| `RunnerContext`（单次运行级） | `RunContext`（本次脚本运行的守护任务表、统计） | 简化 |
| `CancellationContext` | `CancellationToken` | 保留统一取消思想 |
| ClearScript V8 + `EngineExtend.InitHost` | Python 沙箱 + 注入 `ctx`/`g`/工具 | 沙箱白名单（设计实现.md §5.3） |

## 3. 总体架构

```
┌─────────────────────────────────────────────────────────────────┐
│                    AI 脚本运行时 (Runtime)                       │
│                                                                 │
│   ┌─────────────── asyncio event loop (单线程) ───────────────┐ │
│   │                                                            │ │
│   │   守护任务池 (Daemon Registry)                             │ │
│   │     • auto_pick      • auto_skip     • loading_wait        │ │
│   │     • auto_eat       • quick_teleport  …                   │ │
│   │     (各自 async 循环，协作式并发)                           │ │
│   │                                                            │ │
│   │   所有 avc 实际调用 (sc/ic/tm/ocr) 都在此线程执行  ← 关键   │ │
│   └────────────────────────────────────────────────────────────┘ │
│              ▲ run_coroutine_threadsafe        ▲ create_task      │
│              │                                  │                 │
│   ┌──────────┴───────────┐         ┌───────────┴──────────────┐  │
│   │  工作线程 (主脚本)    │         │  mount(name)/unmount(name)│  │
│   │  AI 同步代码          │  g.*    │  由脚本调用               │  │
│   │  task_xxx(ctx, g)     │────────▶│                          │  │
│   │  (to_thread 执行)     │  桥接   │                          │  │
│   └───────────────────────┘         └──────────────────────────┘  │
│                                                                 │
│   ┌─── 共享 ──────────────────────────────────────────────────┐  │
│   │  GameContext (sc/ic/tm/ocr)   RunContext   CancellationToken│  │
│   └────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
        │ avc SWIG (Input/Vision/Image/_core)
        ▼
   C++ avc SDK（截图/输入/模板匹配/OCR）
```

### 三条核心设计决策

1. **同步外壳、异步内核**：AI 写纯同步代码（最友好），引擎内部全 asyncio（并发、取消干净）。AI 脚本跑在一个**工作线程**里（`asyncio.to_thread`），调用 `g.teleport_to()` 等高层 API 时，内部通过 `asyncio.run_coroutine_threadsafe(coro, loop).result()` 把真正的 async 工作提交到 event loop 并阻塞等待。

2. **单线程 event loop 天然解决 avc 并发安全**：这是选 asyncio 方案的**最大技术红利**。avc 的 `sc/ic/tm/ocr` 不是线程安全的，主脚本和守护任务若从不同线程同时调用会冲突。而本架构中**所有 avc 实际调用都在 loop 线程**（协作式调度，协程间不抢占），主脚本的 avc 调用经桥接进入 loop，守护任务的 avc 调用本就在 loop——天然序列化，**无需加锁**。

3. **守护任务 = 自治 async 循环**（非回调）：不再像 BetterGI 那样由调度器每帧回调 `OnCapture`，守护任务自己 `while True: await sleep(间隔); 检测; 响应`。频率自管、逻辑自洽、易写易读。

## 4. 核心抽象

### 4.1 Runtime —— 引擎入口

```python
class Runtime:
    """AI 脚本运行时。单例。持有 event loop、GameContext、守护任务注册表。"""

    def __init__(self, window_title="原神"):
        self.ctx = GameContext(window_title)        # avc 实例 (见 设计实现.md)
        self.g = HighLevelApi(self.ctx)             # 高层语义 API (见 §6)
        self.loop = asyncio.new_event_loop()        # 引擎 event loop
        self.daemons = DaemonRegistry()             # 已挂载守护任务
        self._loop_thread = Thread(target=self.loop.run_forever, daemon=True)

    # ── 主脚本执行 ──
    def run_intent(self, user_intent: str, timeout=600) -> bool:
        """intent → 缓存 → 校验 → 执行 (见 §5)"""
        code = TaskCodeCache.get(user_intent) or self._generate(user_intent)
        ok, err = CodeValidator.validate(code)
        if not ok:
            return False
        return self.run_code(code, timeout)

    def run_code(self, code: str, timeout=600) -> bool:
        """在沙箱执行已校验的脚本代码"""
        token = CancellationToken()
        run_ctx = RunContext(token)
        self._current = (run_ctx, token)
        try:
            # 同步脚本丢到工作线程；loop 在主线程并发跑守护
            future = asyncio.run_coroutine_threadsafe(
                self._run_in_executor(code, run_ctx, token, timeout),
                self.loop,
            )
            return future.result(timeout + 5)
        except KeyboardInterrupt:
            token.cancel("用户中断")
            return False

    # ── 守护任务 (由脚本在工作线程调用,转发到 loop) ──
    def mount(self, name: str, **opts): ...         # 挂载守护任务
    def unmount(self, name: str): ...               # 卸载
    def suspend_all(self): ...                      # 临时挂起全部 (如打开设置菜单)
    def resume_all(self): ...
```

### 4.2 守护任务 Daemon —— 对应 BetterGI `ITaskTrigger`

```python
class Daemon(Protocol):
    name: str
    async def run(self, ctx: GameContext, token: CancellationToken) -> None:
        """自治 async 循环。token 取消时退出。"""
        ...

class AutoPickDaemon(Daemon):
    """自动拾取 — 对应 BetterGI AutoPickTrigger"""
    name = "auto_pick"
    WHITELIST = {"collect", "interact", "item"}
    BLACKLIST = {"enemy_identify"}

    async def run(self, ctx, token):
        g = HighLevelApi(ctx)
        while not token.cancelled:
            dets = await g.detect_objects_async("world")   # avc 调用在 loop 线程
            for cls, items in dets.items():
                if cls in self.BLACKLIST or cls not in self.WHITELIST:
                    continue
                ctx.press(KeyCode.f)
                await asyncio.sleep(0.5)
                break
            await asyncio.sleep(0.1)   # 自管频率 (~10Hz)，无需外部调度器
```

**与 BetterGI 触发器的区别**：

| BetterGI `ITaskTrigger` | avc_genshin `Daemon` |
|---|---|
| 调度器每帧回调 `OnCapture` | 自己 `while + sleep` 循环 |
| `Priority`/`IsExclusive`/`SupportedGameUiCategory` | 无；UI 判断写在守护内部 |
| 由 `GameTaskManager.LoadInitialTriggers` 预加载 | 脚本按需 `mount/unmount`，动态启停 |
| 多触发器由调度器筛选同帧运行 | 多守护在 loop 协作式并发 |

### 4.3 同步桥 —— 让 AI 写同步代码

```python
class HighLevelApi:
    """g.* 高层 API。AI 调用是同步阻塞，内部桥接到 loop 的 async 实现。"""

    def __init__(self, ctx: GameContext):
        self.ctx = ctx
        self._loop = Runtime.instance().loop

    def _call(self, coro):
        """同步外壳 → async 内核：提交到 loop 并阻塞等待。检查取消。"""
        token = Runtime.instance().current_token
        token.check()                                   # 取消点
        fut = asyncio.run_coroutine_threadsafe(coro, self._loop)
        try:
            return fut.result()
        finally:
            token.check()

    # ── 高层语义 (AI 友好) ──
    def teleport_to(self, name: str): return self._call(self._teleport(name))
    def go_to(self, pos): return self._call(self._navigate(pos))
    def talk(self, option: str): return self._call(self._talk(option))
    def wait_text(self, kw, timeout=10): return self._call(self._wait_text(kw, timeout))
    # ... 见 §6
```

> `sleep(s)`、`wait_until(pred, timeout)` 等工具同理：同步阻塞、内部检查 `token.check()`，被取消时抛 `CancelledError`。

### 4.4 RunContext + CancellationToken

```python
class CancellationToken:
    """统一取消：Ctrl+C / 用户停止 / 超时。主脚本与所有守护共享。"""
    def __init__(self): self._cancel = False; self.reason = None
    def cancel(self, reason=""): self._cancel = True; self.reason = reason
    @property
    def cancelled(self): return self._cancel
    def check(self):
        if self._cancel: raise CancelledError(self.reason)

class RunContext:
    """单次脚本运行的状态。"""
    def __init__(self, token): self.token = token; self.mounted = []; self.started_at = time.time()
```

## 5. 脚本加载与执行流程

```
用户意图 (自然语言)
    │
    ▼
① TaskCodeCache.get(intent)  ──命中──▶ code
    │ 未命中                           │
    ▼                                  │
② AITaskPlanner.plan(intent, state)   │   (LLM,见 genshin_daily_design.md §5.5)
    │                                  │
    ▼                                  │
③ CodeValidator.validate(code)  ◀──────┘   AST 白名单校验 (禁 import/危险内置)
    │
    ▼
④ TaskCodeCache.put(intent, code)          md5(intent) → cache/<hash>.py
    │
    ▼
⑤ Runtime.run_code(code)
    │  ├─ 新建 CancellationToken + RunContext
    │  ├─ 沙箱 globals = {ctx, g, sleep, wait_until, KeyCode, print, ...}  (设计实现.md §5.3)
    │  ├─ exec(code, sandbox_globals)            定义 task_xxx
    │  └─ 工作线程调用 task_xxx(ctx, g)          主脚本同步执行
    │       └─ 期间 ctx.mount("auto_pick") → loop 起 AutoPickDaemon 并发
    ▼
⑥ 完成 / 取消 / 超时  →  卸载所有守护  →  ReleaseAllKey
```

**热加载**：脚本以 `.py` 文件缓存于 `cache/tasks/`。再次相同 intent 直接 `exec` 已缓存代码，跳过 LLM（1–3s → 毫秒级）。改 intent 或清缓存即重新生成。

**沙箱**（沿用 `设计实现.md` `CodeValidator` + `safe_globals`）：AST 禁 `import`/`open`/`exec`/`eval`/`__import__`/下划线属性；`globals` 仅注入白名单对象与内置（`len/range/int/...`）、`math/time/random`、`KeyCode`。

## 6. AI 友好的 API 表面

**设计原则**：让 AI 写高层语义、少接触 avc 原始 API。三层 API，由高到低：

### 第一层：高层语义 `g.*`（AI 默认用这层）

```python
# 移动/导航
g.teleport_to("蒙德城")              # 传送
g.go_to(npc_pos)                    # 小地图定位 + 走过去（走动中守护并发）
g.talk("领取每日委托奖励")          # 对话中找选项并点
g.talk_skip()                       # 跳过对话

# 等待
g.wait_text("委托", timeout=10)     # 等文字出现
g.wait_template("templates/x.png")  # 等模板出现
g.wait_main_ui(timeout=30)          # 等回到大世界

# 检测（返回高层结果，不返回原始 bytes）
g.has_enemy()
g.find_nearest_enemy()
g.is_loading()

# 操作（坐标基于 1080p）
g.click(960, 540)
g.press(KeyCode.f, hold=0)
```

### 第二层：`ctx.*` + `vision.*`（降级时用，对应 设计实现.md `GameContext`/`VisionUtils`）

```python
ctx.capture(); ctx.click_at(x,y); ctx.press(KeyCode.e)
vision.find_template("templates/x.png"); vision.find_text("委托"); vision.detect_objects("world")
```

### 第三层：守护任务 `ctx.mount/unmount`（并发响应）

```python
ctx.mount("auto_pick")              # 边走边按 F
ctx.mount("auto_skip")              # 自动跳对话
ctx.mount("loading_wait")           # 加载自动等待
ctx.unmount("auto_pick")
ctx.suspend_all(); ctx.resume_all() # 临时挂起（如进设置菜单）
```

> AI prompt 模板（`genshin_daily_design.md §5.4`）应优先引导用第一层，必要时降到第二层，并发需求用第三层。

## 8. 关键设计权衡

### 8.1 为什么 asyncio 而非线程
- **avc 并发安全**：单线程 loop 让所有 avc 调用序列化，免锁（§3 决策 2）。线程方案需对 `sc/ic/tm/ocr` 全部加锁，且 GIL 下 YOLO/OCR 推理仍争抢。
- **取消干净**：`token.cancel()` + `task.cancel()` 传播到所有协程；线程要靠 `Event` 轮询 + 中断点，难彻底。
- **AI 友好不减分**：通过同步桥，AI 仍写同步代码，不感知 async。

### 8.2 为什么放弃 BetterGI 的优先级/独占/UI 场景调度（并发安全详见 `02-可靠性三件套.md` §1-2）

- BetterGI 的 `Priority`/`IsExclusive`/`SupportedGameUiCategory` 是**调度器侧**的复杂机制——AI 难正确配置，也违背"代码即流程"。我们放弃这套机制，**但不放弃它解决的正确性问题**。
- 替代方案用更轻、更透明的方式达到同等可靠性（详见 `02-可靠性三件套.md`）：
  - **输入通道权属**（`InputAuthority` + `owns_keys`）：守护声明碰哪些输入通道，框架保证同通道同一时刻只有一个写者，或按 `priority` 仲裁。"边走边拾取"合法（`go_to` 持 `MOVE`、`auto_pick` 持 `INTERACT`，不冲突）；两个都想按 F → 被框架拒绝（抛 `InputConflict`）。
  - **场景门控**（`scenes=` + `SceneEstimator`）：守护声明活跃场景，由常驻场景估计器判定，不符自动 suspend。`auto_pick` 在对话/菜单/战斗里**根本不启动**——从根上消掉"误按 F 弹面板"。
- **⚠️ 修订原先的判断**：本节早先版本把并发冲突说成"**极少、靠脚本 `mount` 顺序或 `suspend_all` 规避**"——那是**低估**。野外 `auto_pick` 的 F 会触发宝箱/NPC/七天神像/秘境入口/调查点的交互面板，是**高频副作用**，必须由框架保证，而非靠任务自觉。
- `suspend_all`/`resume_all` **保留**，但降级为：主任务进入"不可打断段"（战斗连招、设置菜单）时的**显式逃生口**，而**非**并发安全的依赖。

### 8.3 主任务与守护的协作（简化 BetterGI 互斥）
- BetterGI：独立任务启动时**清空所有触发器**。新项目：守护可与主任务**并存**（这正是"边走边拾取"要的）。
- 仅当主任务进入不该被打断的流程（如设置菜单、战斗连招），脚本显式 `ctx.suspend_all()` / `unmount`。
- 不需要 `TaskSemaphore(1,1)`：Runtime 对 intent **串行执行**（一次跑一个主脚本），天然互斥。

### 8.4 失败/超时/取消的统一出口
- 任何异常（含 `CancelledError`、超时、`NormalEndException`）→ Runtime 捕获 → **卸载所有守护** + `ReleaseAllKey()`（对应 BetterGI `TaskRunner.End()`）→ 保证游戏不留按住的键。

## 9. 与 BetterGI 执行引擎的完整对照

| 维度 | BetterGI | avc_genshin | 取舍 |
|---|---|---|---|
| 主任务抽象 | `ISoloTask.Start(ct)` | AI 脚本 `task_xxx(ctx, g)` | 借鉴契约，简化为约定函数 |
| 主任务执行 | `TaskRunner` + `TaskSemaphore(1,1)` | `Runtime.run_code` 串行 | 去 mutex，Runtime 天然串行 |
| 并发响应 | `ITaskTrigger.OnCapture` 每帧回调 | `Daemon.run` async 循环 | 从回调变自治循环，去优先级/独占 |
| 启动时挂起触发器 | `ClearTriggers` → 任务结束 `LoadInitialTriggers` | 脚本按需 `mount/unmount` | 交给脚本控制，更灵活 |
| 取消 | `CancellationContext` | `CancellationToken` + 桥接检查点 | 保留思想，覆盖同步+异步 |
| 游戏会话上下文 | `TaskContext`（GameHandle/PostMessage/Dpi） | `GameContext`（avc sc/ic/tm/ocr） | 换底层，职责不变 |
| 单次运行上下文 | `RunnerContext`（队伍/暂停/CombatScenes） | `RunContext`（守护表/统计） | 简化 |
| 截图归一化 | `CaptureContent.DeriveTo1080P` | avc `IScreenCapture` + 约定 1080p | 职责下沉到 avc |
| 脚本宿主注入 | ClearScript V8 `EngineExtend.InitHost` | Python 沙箱 globals 注入 | 沙箱白名单 |

## 10. 开放问题（待后续细化）

## 11. 扩展点（预留）：运行时决策层

> **状态：仅预留接缝，不实现。** 对标 BetterGI 的核心能力（导航/战斗/任务体系，§10 阶段七~八、`设计实现.md` M5）完成后再做。现在钉死接口，使将来接入**无需改主控制流**。

「代码即流程」要求控制权在 Python。但流程中途可能遇到**确定性 CV 裁决不了**的不确定（未知 UI、多义选项、卡死状态）。为此预留一个**可插拔运行时决策层**：流程或框架在此处向"外部决策者"（未来：LLM / VLM / 人在环）提问，拿**结构化结果**回流程，由 Python 代码决定下一步。决策者是流程的一个**调用点**，不是驱动者——这条边界不可越。

**接缝 A —— 流程侧 `g.decide`**（与 `g.wait_text` 同层的高层 API，任务侧主动问）：

```python
@dataclass
class Decision:
    answer: dict          # 符合 schema 的结构化答案
    confidence: float     # [0,1]；低于阈值时流程应自行降级（跳过/问人/中止）
    source: str           # "cv"|"llm"|"vlm"|"human"（命中了决策链的哪一档）
    rationale: str        # 理由，供可观测/调试

class HighLevelApi:
    def decide(self, question, schema, *, context="auto", timeout=30) -> Decision: ...
    # 同步外壳、检查 token、可超时。用法：r = g.decide(...); if r.confidence > 0.7: ...
```

**接缝 B —— 框架侧 `Runtime.on_uncertain`**（钩子，默认 no-op；框架被动求救）：

```python
class Runtime:
    def on_uncertain(self, event) -> Decision | None:
        """框架检测到不确定（unknown_scene / stuck / unexpected_scene）时调用。
        默认 return None（走原失败处理）；接入后改为 self._decider.decide(...)。"""
        return None
```

**决策者抽象**（实现后置）：

```python
class Decider(Protocol):
    def decide(self, question, schema, context) -> Decision: ...
class NoOpDecider(Decider):                       # 现阶段的唯一实现
    def decide(self, *a, **k): raise NotImplementedError("决策层后置（见 §11）")
```

> 将来接入时：**只替换 `Decider` 注入 + 接上 `on_uncertain`**；`g.decide` 的签名、调用它的任务代码、主失败处理流——**全部不变**。这就是"留口子"的全部含义：现在不写一行决策逻辑，但接缝已固定，后置实现零回改。
