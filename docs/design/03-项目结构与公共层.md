# 03 · 项目结构与公共层 —— 工程骨架

> 本文档定 avc_genshin 的**工程骨架**:目录分层、公共层(所有任务共用的横切能力)、游戏资源组织、结构化日志。
> 前置:`00-框架总纲` / `01-执行引擎` / `02-可靠性三件套`。
> **这是"代码文件夹怎么分"的权威答案**;`IMPLEMENTATION §9`、`CLAUDE.md §7`、`00 §8` 均以本文为准。

---

## 0. 一句话

**所有代码进 `src/`,平铺为 `framework/` `abilities/` `tasks/` 三个顶层包(无外层包名);资源 `resources/`、产物 `cache/ logs/ debug/` 留在包外。** 三类分离:**代码 / 资源 / 产物**。根目录除文档外没有散落的 `.py`。

---

## 1. 为什么 src layout(平铺三包)

| | flat(`framework/` 在根) | **src 平铺(`src/framework` `src/abilities` `src/tasks`)✅** |
|---|---|---|
| import 意外 | 测试时可能误导入根目录模块 | 隔离干净,`pip install -e .` 后 import |
| 代码 vs 资源 vs 产物 | 全堆在根目录,边界模糊 | 代码进 src、资源/产物在包外,**物理隔离** |
| 包结构 | — | 三个职责清晰的顶层包:`framework`(引擎+公共层)、`abilities`(领域能力)、`tasks`(插件) |
| AI 写任务 | — | `from framework import task, KeyCode`(简短直观) |

代价:需 `pip install -e .`(开发期一次性)。本项目本地运行、不发布 PyPI,顶层包名(`framework`/`abilities`/`tasks`)可接受。

> **三个顶层包的职责**:
> - `framework/` —— 执行引擎 + 公共层(Runtime/任务体系/守护/可靠性地基/GameContext/配置/资源/异常/工具)。**AI 写任务时 import 的对象**。
> - `abilities/` —— 游戏领域能力(导航/战斗/检测/视觉工具/状态)。任务按需 `from abilities import navigation`。
> - `tasks/` —— L3 任务插件(AI 写入;内置示例进 git)。框架扫描加载,不直接 import。

## 3. 三类分离的约定

| 类 | 位置 | 谁写 | 进 git | 打包 | 例子 |
|---|---|---|---|---|---|
| **代码** | `src/`(`framework/` `abilities/` `tasks/`) | 人 + AI 维护 | ✅ | framework+abilities ✅ | `runtime.py` `daily_quest.py` |
| **资源** | `resources/`(包外) | 人截取 / 复用 BGI | 小文件✅ 大文件❌ | ❌ | `templates/*.png` `models/*.onnx` |
| **产物** | `cache/ logs/ debug/`(包外) | 运行时生成 | ❌ | ❌ | `logs/r_2026....jsonl` |

> **打包**:`pyproject.toml` 用 `[tool.setuptools.packages.find] where=["src"]`,发现并打包 `framework` + `abilities`。`tasks/` 是插件目录,**随仓库 git(内置示例),但运行时扫描加载,不作为 import 包**(框架用 `importlib` 按文件加载单个任务)。
>
> **核心纪律**:AI 写任务只往 `src/tasks/`(持久)或 `cache/tasks/`(即时)写;AI 不会也不应改 `framework/` `abilities/`(那是框架本体)。这条边界让"AI 添加任务"安全——AI 的写入域被物理限制在 tasks 子目录。

## 4. tasks/ —— src/tasks/(与 framework/abilities 平级)

- **位置**:`src/tasks/`,与 `framework/` `abilities/` 同级。所有 Python 代码统一在 src,根目录只留文档/资源/产物。
- **约定不变**:一文件一任务、`@task(name/desc/daemons/requires/params)` + `def main(ctx, g, **params)`(契约见 `00 §3`、详 见 `04-任务契约与注册.md`)、import `from framework import task, KeyCode`。
- **AI 写入域隔离仍成立**:AI 只往 `src/tasks/` 写,**不改** `framework/` `abilities/`——写入域被限制在 tasks 子目录。
- **发现 / 热加载**:Runtime 扫描**两个根**——`src/tasks/`(持久任务)+ `cache/tasks/`(即时任务,`<hash>.py`)。框架用 `importlib` 按文件加载,文件变更 watcher 触发 `registry.reload(name)`,无需重启。
- **打包 / git 策略(关键)**:
  - `src/tasks/` 下的任务文件**进 git**(人/AI 审定过的持久任务;内置示例随仓库)。
  - `tasks/` **不打包**(不是 import 包,是扫描目录),新装机从 git 拿到内置任务。
  - AI 运行时**临时**生成的任务走包外 `cache/tasks/`(gitignore),不污染 src。
  - 即时任务"提升"为持久任务时,才从 `cache/tasks/` 移入 `src/tasks/` 并补元数据、提交。
- **即时任务**:intent 现场生成的脚本缓存到包外 `cache/tasks/<hash>.py`(产物,非代码,gitignore)。成熟后提升为持久任务(`00 §3.2`)。

## 5. resources/ 资源组织 + 资源定位器

### 5.1 子目录约定

| 子目录 | 内容 | git | 来源 |
|---|---|---|---|
| `templates/` | 模板图(按功能再分子目录:`daily/` `domain/` `ui/common/`) | ✅ | 自截 / BGI |
| `paths/` | BetterGI 路径 JSON | ✅ | BGI 社区 |
| `models/` | ONNX 模型(world/avatar/...) | ❌ 大文件 | BGI Release |
| `ocr/` | OCR 模型/字典 | ❌ | BGI / avc 内置 |
| `map/` | 全地图数据(300M+) | ❌ | BGI Release |

### 5.2 资源定位器 `res`(统一访问,禁止硬编码相对路径)

```python
# src/framework/resources.py
class Resources:
    def __init__(self, root: Path, bgi_root: Path | None):
        self.root = root; self.bgi_root = bgi_root
    def path(self, rel: str) -> Path:
        """先查 resources/<rel>;不存在且配了 BGI_ROOT → 查 BGI 对应路径(免复制)。"""
        p = self.root / rel
        return p if p.exists() else self._bgi_fallback(rel)
    def template(self, name): return self.path(f"templates/{name}")
    def model(self, name):    return self.path(f"models/{name}")
    def path_json(self, name):return self.path(f"paths/{name}")

res = Resources(root=Path("resources"), bgi_root=Path(os.getenv("BGI_ROOT", "")) or None)
```

- 任务/框架都用 `res.template("daily/katherine.png")`、`res.model("bgi_world.onnx")`,**不写** `"../resources/..."`。
- **复用 BetterGI 不复制**:设 `BGI_ROOT=D:/Work/github/better-genshin-impact`,定位器找不到本地资源时回退到 BGI 目录。模型/全地图这种大文件直接读 BGI,零拷贝。
- **大文件 gitignore**:`resources/models/`、`resources/map/` 进 `.gitignore`;提供 `scripts/fetch_resources.py` 从 BGI Release 下载或建符号链接。

### 5.3 模板图约定

- **1080p 基准**:所有模板在 1920×1080 下截取;匹配前由 avc `IScreenCapture` 归一化(`00 §8`)。
- **纯绿透明**:需要忽略背景的模板用纯绿 `(0,255,0)` 填充,`tm.setGreenMask(True)`(`IMPLEMENTATION §5.4`)。
- **命名**:`<功能>/<元素>[_状态].png`,如 `daily/katherine.png`、`ui/common/confirm_btn.png`。

## 6. 公共层(Common Layer)—— 所有任务共用的横切能力

"公共层"= 相对具体业务需求、**所有任务与执行过程都会用到**的能力。它们在 `src/framework/`(框架核心),任务作者**透明使用**,多数无需感知。

| 公共能力 | 模块 | 作用 | 详见 |
|---|---|---|---|
| **GameContext** | `framework/context.py` | avc 实例(sc/ic/tm/ocr)单一入口 | IMPL §4.1 |
| **高层 API `g.*`** | `framework/high_level_api.py` | 操作语义(teleport/go_to/talk/wait_*) | 01 §6 |
| **SharedState** | `framework/shared.py` | scene/frame 共享事实源 | 02 §1 |
| **InputAuthority / Policy** | `framework/authority.py` `policy.py` | 并发安全 + 护栏(透明拦截) | 02 §2 §5 |
| **结构化日志** | `framework/logging.py` + `observe.py` | **AI 可解析的运行日志**(本篇 §7) | §7 |
| **资源定位器 `res`** | `framework/resources.py` | 统一访问模板/路径/模型 | §5 |
| **配置 `config`** | `framework/config.py` | 窗口/分辨率/模型路径/拟人化 | §9 |
| **统一异常** | `framework/errors.py` | NormalEnd/Retry/TaskError/InputConflict/PolicyViolation/... | 02 §4 |
| **工具函数** | `framework/utils.py` | sleep/wait_until/坐标转换/1080p 归一化/RNG 种子 | — |
| **守护库** | `framework/daemons/` | 可复用并发响应器(auto_pick/skip/...) | 01 §7 |

> 这些就是"共同层"。任务 `main(ctx, g)` 里的 `ctx`/`g` 是它们的入口;任务作者**不必**直接 import 大多数——`g.wait_template(res.template("x.png"))` 一行就串起了 资源定位器 + 高层 API + SharedState + Observe。

## 7. 结构化日志(AI 可解析)—— 本篇重点

### 7.1 目标

每次任务执行产出**机器可读的结构化日志**,让 AI 能读日志→理解结果→定位失败→改进任务。这是"AI 全程处理"闭环里**观察环节**的标准化(`02 §4` 可观测性的持久化层)。

### 7.2 格式:JSONL(每行一条事件)

落盘到 `logs/<run_id>.jsonl`,一行一个 JSON 对象:

```json
{"ts":0.12,"run_id":"r_20260804_153022","task":"daily_quest","scene":"main_ui","level":"info","event":"task_start","params":{"count":4}}
{"ts":12.34,"run_id":"r_20260804_153022","task":"daily_quest","scene":"main_ui","level":"info","event":"action","action":"press","key":"f","result":"ok"}
{"ts":12.40,"run_id":"r_20260804_153022","task":"daily_quest","scene":"main_ui","level":"debug","event":"detect","cls":"interact","items":[{"x":800,"y":600,"score":0.91}]}
{"ts":12.55,"run_id":"r_20260804_153022","task":"daily_quest","scene":"dialog","level":"warn","event":"scene_change","from":"main_ui","to":"dialog"}
{"ts":45.21,"run_id":"r_20260804_153022","task":"daily_quest","scene":"main_ui","level":"info","event":"task_return","return_value":{"claimed":true}}
```

失败时:

```json
{"ts":30.77,"run_id":"r_20260804_153022","task":"daily_quest","scene":"unknown","level":"error","event":"failure","failure_type":"UnexpectedScene","expected":"main_ui","got":"unknown","shot":"debug/r_20260804_153022/30.77_unknown.png","timeline_tail":[...]}
```

### 7.3 字段约定

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | float | 相对运行开始的秒数 |
| `run_id` | str | 运行标识(含日期时间),同一运行所有事件共享 |
| `task` | str | 当前任务名(框架级事件可空) |
| `scene` | str | 当前场景(来自 `SceneEstimator`,02 §1) |
| `level` | str | `debug`/`info`/`warn`/`error` |
| `event` | str | 事件类型:`task_start`/`action`/`detect`/`scene_change`/`wait`/`mount`/`unmount`/`task_return`/`failure`/... |
| `result` | str | `ok`/`fail`/具体(动作类事件) |
| `failure_type` | str | 失败时必填,取 `02 §4.3` 的分类(`UnexpectedScene`/`TemplateNotFound`/`StuckAt`/`InputConflict`/`Timeout`/`PolicyViolation`) |
| `shot` | str | 失败存证截图路径(指向 `debug/<run_id>/...`) |
| 其余 | — | 按 `event` 类型自由扩展 |

### 7.4 产出方式

- `framework/logging.py`:JSONL 序列化器,每次运行开 `logs/<run_id>.jsonl`。
- `framework/observe.py`(02 §4)的 `event()` 同时**追加到内存时间线**和**写 JSONL**。
- 任务 `main` 的**返回值**由 Runtime 自动记一条 `task_return`;**异常**自动记 `failure` + 存证截图。任务作者**不用手写日志**——`g.*` 的每次调用框架已记录。

### 7.5 AI 如何用它迭代

```
任务失败 → Runtime 记 failure 事件(带 failure_type + 截图 + timeline_tail)
        → AI 读 logs/<run_id>.jsonl 的 failure 行 + 看截图
        → 据 failure_type 定向修正(如 TemplateNotFound → 更新模板/ROI;UnexpectedScene → 补场景处理)
        → 改 src/tasks/<name>.py → 热加载 → 重跑
```

失败类型与修正动作的映射见 `02 §4.3`。**结构化日志 + 失败分类 = AI 能精准改,而非整段重写。**

## 8. 执行流程串联(指向 01/02)

```
main.py(薄壳)/ python -m framework 接收 intent/--task
  → Runtime.run_intent/run_task                    [01 §4.1]
  → 生成 run_id;开 logs/<run_id>.jsonl;启 SceneEstimator/FrameDaemon 守护  [02 §1 §3]
  → TaskRegistry 取任务(扫描 src/tasks/ + cache/tasks/)→ 沙箱 exec  [01 §5]
  → 工作线程跑 main(ctx,g):
       g.* 每次调用 → 租用 InputAuthority[02 §2] · 读 SharedState[02 §1] · 过 Policy[02 §5] · 写 Observe/JSONL[§7]
       ctx.mount(...) → 守护并发(场景门控+权属保证安全)[02 §2]
  → 返回值记 task_return;异常记 failure + 存证
  → 结束:卸载所有守护 + ReleaseAllKey + 关日志      [01 §8.4]
```

完整执行引擎细节见 `01`,可靠性地基见 `02`,本文只补"这些发生在哪个目录、产出落到哪"。

## 11. 开放问题

1. **tasks git 策略**:`src/tasks/` 进 git(持久任务);AI 临时生成的在 `cache/tasks/`(gitignore)。提升机制(cache→tasks)需明确**何时自动提交** vs **待人工审定**。
2. **顶层包名冲突**:`framework`/`abilities`/`tasks` 是泛名,本地运行无碍;若未来发布 PyPI 需改命名空间(如 `avcgs_framework`)。
3. **多实例/多账号**:GameContext 单例假设单游戏窗口;若要多开,`tasks/` 与 `logs/<run_id>` 如何隔离(可能需 session_id 维度)。
4. **资源版本化**:BGI 模型/路径随游戏版本失效;`resources/` 是否需要版本目录(`resources/4.x/`)与版本探测。
5. **日志体积**:长时运行 JSONL 膨胀;需要轮转/压缩/按 run_id 清理策略。
6. **配置热更**:运行中改 `config.toml` 是否热生效(部分项如阈值可热更,窗口名不可)。
